### QIDO 延迟 vs 并发（workers=1，`wrk --latency`）

| 并发 | QPS | P50 | P90 | P99 |
|---|---|---|---|---|
| 1 | 1569 | 0.33 ms | 41 ms | 55 ms |
| 10 | 1365 | 3.6 ms | 60 ms | 75 ms |
| 50 | 1486 | 40 ms | 82 ms | 89 ms |
| 200 | 1428 | 115 ms | 188 ms | 195 ms |

> P50 极低（0.33 ms）说明单请求处理快；P99 随并发增长主要来自**排队**；
> 低并发下的长尾（P90/P99 数十 ms）来自 **worker↔IO 线程的唤醒/调度延迟**
> （多线程架构固有开销，容器共享 CPU 下更明显）。降低长尾的方向：同步处理或 worker 自旋。

## 优化记录（供面试讲"怎么调优"）

| # | 问题 | 定位手段 | 修复 | 前后指标 |
|---|---|---|---|---|
| 1 | QIDO 大结果集慢 | wrk + 分离 404/QIDO 路径 | JSON 用 string 拼接替代 ostringstream | 163 → 180 QPS |
| 2 | 多 worker 反而更慢 | workers 1/2/4/8 曲线 | MetadataDao 每线程独立只读连接（NOMUTEX） | workers=8：161 → 345 QPS |
| 3 | SQLite 并发读负扩展 | worker 数曲线 | 调优结论：查询密集负载用更少 worker（workers=1 最优），高并发应换 PostgreSQL | 1264(1) > 990(2) > 676(4) > 342(8) |
| 4 | 大 body（>100KB）请求 404 | 按 body 大小梯度探测 | HttpParser 中间状态由 parser 自持（原实现跨多次 Parse 丢失 method/path） | 1KB~16MB 全部 200 |
| 5 | WADO 实例端点与 Orthanc 不一致 | 与 Orthanc 互操作对比 | 按 PS3.18 默认返回 multipart/related | INTEROP PASS |

```bash

# 单测 + 覆盖率
```
